---
title: Runtime secrets in Vault
description: Vault paths, deployment prerequisites, and runtime credential loading.
---

The API and flat-file worker read S3 settings and application encryption keys
from Vault in every deployment. TEST and PROD also read database credentials
from Vault. PR previews use their own generated PostgreSQL credentials.

## Secret paths

Use the following base paths with the Vault CLI or UI.

| Environment | Base path |
| --- | --- |
| DEV and PR previews | `b5cfc6-nonprod/address-change-api-dev` |
| TEST | `b5cfc6-nonprod/address-change-api-test` |
| PROD | `b5cfc6-prod/address-change-api-prod` |

Create these entries below the base path. Store every field as a string.

| Entry | Fields | Environments |
| --- | --- | --- |
| `address-change-s3` | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `FLAT_FILE_S3_BUCKET`, `FLAT_FILE_S3_ENDPOINT`, optional `AWS_REGION` | All |
| `address-change-app` | `ADDRESS_CHANGE_ENCRYPTION_KEYS`, `SFTP_CREDENTIAL_ENCRYPTION_KEY` | All |
| `address-change-db/runtime` | `username`, `password` | TEST, PROD |
| `address-change-db/migration` | `username`, `password` | TEST, PROD |

The deployment uses KV v2 API paths, inserting `/data/` after the mount name.
Copy existing database and encryption values exactly. The request encryption
key ring remains a string containing JSON, including all historical key IDs.
The SFTP encryption field is a separate base64-encoded 32-byte key. Generate
one only when no existing encrypted partner credentials depend on an older key.

## Startup

The platform injector authenticates `b5cfc6-vault` and renders JSON files before
application initialization. Missing secrets or required fields block startup.
The API and worker use the generic Node loader for S3, app keys, and runtime
database credentials. The worker's annotations include only these runtime groups.
The API pod additionally requests migration credentials for Flyway. The migration
file is rendered into a dedicated memory-backed volume shared only by the Vault
init container and Flyway. The API and worker receive only runtime secret files.

Flyway's image includes a wrapper that reads migration credentials from JSON
when `VAULT_DATABASE_ENABLED=true`. It uses its normal environment-based
credentials for local development and PR previews. The wrapper exports the
Vault username and password before invoking Flyway.

The template retains required database Secret references for disposable PR
databases. In TEST/PROD those references are optional, and the application
explicitly overwrites any compatibility values with
Vault credentials and require both database fields from Vault. A missing Vault
value fails startup even if the old OpenShift Secret still exists.

The loader rejects duplicate keys across files. It permits overwriting an
existing variable only if it is listed in `VAULT_OVERRIDE_KEYS`. The deployment
lists `POSTGRES_USER` and `POSTGRES_PASSWORD` for database migration compatibility.
Database host, name, TLS settings, OIDC configuration, and the active encryption
key ID remain deployment configuration.

## Rollout and verification

Build new backend and migrations images when deploying this change. Confirm the
Vault service account can pull both images. First test a PR preview to verify
that its disposable database credentials still work, then deploy TEST.

Confirm the Vault init container, migrations, and API become Ready. Validate
existing request decryption, a synthetic request round trip, and the flat-file
worker's access to PostgreSQL and S3. See [S3 access testing](./flat-file-s3-test).
Updated Vault values take effect on API pod restart and when new worker pods
start.
