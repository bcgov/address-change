# Address Change database recovery

Use this procedure to restore an S3 backup into a fresh PostgreSQL database. The
recovery Job restores the application schema and data and applies database-specific
grants. It uses the roles established by the bootstrap chart.

## 1. Choose the recovery point and target

- For data corruption or accidental deletion, use the existing Patroni cluster
  if it is healthy and has room for another database, its indexes, and restore
  WAL. Use a fresh database name so the original is available for investigation
  and rollback.
- For cluster or storage loss, provision a replacement PostgreSQL 18 Patroni
  cluster and run the [bootstrap chart](../address-change-db-bootstrap/README.md).
  For the standard release layout, run `provision-patroni`, `bootstrap`, and
  `deploy-backup` in order using the [database operations workflow](README.md#github-actions).
  Bootstrap creates the roles and an empty application database. Choose a
  different, unused name for the restore. Configure the backup chart for the
  replacement endpoint, Patroni superuser Vault entry, and network policy selector.
  Prepare application access to the replacement Patroni service.
- Record the environment, original database, target database, and S3 object
  filename. For corruption, select a known-good archive from before the incident.
  Archive filenames generated by this chart use UTC. Preserve the selected
  archive if it is close to lifecycle expiry.
- For a drill, use a synthetic record known to be in the selected archive. Keep
  the application connected to its current database.

## 2. Prepare the recovery namespace

Use the chart revision containing the restore fix that preserves PostgreSQL's
`\unrestrict` command. The Job mounts scripts from the installed release's
ConfigMap, so upgrade the S3 backup release with that revision before creating
the Job. Follow the [S3 installation instructions](README.md#s3-storage-and-recovery).
Use the same release name and namespace for installation and recovery.

Prepare the [Vault database paths](../address-change-db-permissions/VAULT.md)
in the target environment, including the surviving archive's S3 credentials.
The recovery Job loads the Patroni superuser and the existing migration/runtime
usernames directly from Vault. Preserve the original values. Use the same
Vault configuration when installing the backup release and rendering the
recovery Job. Add the `vault` values shown in the migration guide to
`test-s3.yaml`.

The configured migration and runtime role
names must match the archive's owners and grants. The staging volume needs space
for the compressed archive and its uncompressed SQL. Provision any extensions
required by the application schema on the target database's template or as
part of target preparation.

During an incident, stop application writers, including migrations and
background jobs, before cutover. Record the original configuration and replica
counts, and account for autoscalers or automation that could restart writers.

## 3. Restore the archive

In GitHub Actions, run **Address Change database operations** with
`operation=recover`, the target environment, an unused `recovery_database`,
and the selected filename in `recovery_archive`. The workflow reports the
Job result and leaves the database available for validation. For a replacement
cluster with custom chart values, use the command below. See
[GitHub Environment setup](README.md#github-actions).

From the `address-change` root, use the reviewed S3 values for the target. The example
uses TEST. Replace the archive placeholder with the exact filename in the
configured prefix. Omit the object override only if you intend to restore the
latest timestamped archive, such as for a drill.

```sh
chart=./helm/charts/address-change-db-backup
namespace=b5cfc6-test
release=address-change-db-backup
target=address_change_recovered
archive=REPLACE-WITH-KNOWN-GOOD-ARCHIVE.sql.gz

helm dependency build "$chart"
helm template "$release" "$chart" -n "$namespace" \
  -f "$chart/environments/test.yaml" -f test-s3.yaml \
  --set recovery.enabled=true \
  --set-string recovery.database="$target" \
  --set-string recovery.object="$archive" \
  --show-only templates/recovery-job.yaml > /tmp/address-change-recovery-job.yaml
```

Review the rendered Job before creating it.

```sh
job=$(oc -n "$namespace" create -f /tmp/address-change-recovery-job.yaml -o name)
oc -n "$namespace" logs -f "$job" -c restore --pod-running-timeout=2m
oc -n "$namespace" wait --for=condition=complete "$job" --timeout=65m
```

Confirm the selected archive and database in the logs and check that OpenShift
reports completion.

If the Job fails, use `oc describe` on the Job and its pod. Check
`oc logs "$job" -c install-s3-client -n "$namespace"` for init failures.
Restore failures can report a PostgreSQL SQLSTATE and script line. A failed SQL
transaction can leave the newly created database allocated. Keep it for
investigation or remove it after confirming its identity and use a fresh target
for the retry.

## 4. Validate and cut over

1. Connect to the recovered database with the application runtime credentials.
   Confirm the connection with `SELECT current_database(), current_user;`.
2. Compare affected records and expected counts with the chosen recovery point.
   Check Flyway history, application permissions, and API behavior. For a drill,
   look up the synthetic record by its ID and compare its values.
3. For an incident, confirm writers are paused. Set the backend deployment's
   `DB_NAME` to the recovered database. On a replacement cluster, update the
   service endpoint and Vault paths as well. Check runtime and migration
   access and smoke-test the application before resuming writes.
4. Set the S3 backup chart's `database.name` to the recovered database and
   update the endpoint, Vault paths, and network policy selector if the cluster
   changed. Run a manual backup and S3 verification using the commands in the
   [backup README](README.md#s3-storage-and-recovery).

Keep the original database while rollback is still needed. Before new writes,
rollback can switch the application configuration back if the original is
usable. After new writes, assess and reconcile them before switching back.

## 5. Close the drill or incident

Record the archive, recovery duration, data-loss window, and validation results.
After a drill, disconnect clients from the scratch database and confirm its
name before dropping it. Remove the recovery Job and any temporary ConfigMaps
created for the drill once their logs are captured.

Patroni cluster and completed successfully after the dump trailer fix.
